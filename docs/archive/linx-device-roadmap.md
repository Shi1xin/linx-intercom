# 灵矽同频设备与 MCP 接入方案

## 产品定位与决策

同频是一种默认接入灵矽平台、具备群语音能力的灵矽设备。设备平时承载灵矽智能体对话；NFC 触碰或智能体工具调用使设备进入对讲，退出后回到灵矽对话。设备、智能体和账号关系沿用灵矽 App 与平台

同频同时提供两种接入形态：

| 形态 | 用户体验 | 实现入口 |
| --- | --- | --- |
| 灵矽同频设备 | 对设备说“加入三一四一五九”，或触碰标签，直接开始对讲 | 固件接入灵矽，向当前设备会话声明端侧 MCP 工具；NFC 直接调用本地房间操作 |
| 同频 MCP 服务 | 智能体调用同频工具，让已关联的同频设备进入、切换或退出房间 | 云端 MCP 服务复用同频控制连接，向目标设备下发操作 |

本轮采用以下路线：

- 以已合并的同频固件为起点，增加灵矽协议适配与音频模式管理
- 复用平台 ASR、智能体意图理解和 TTS；设备保留按键触发命令、NFC 和确定性的房间操作
- 设备 MCP、云端 MCP、NFC 共用房间操作与结果确认，媒体继续走 Janus AudioBridge
- 今晚先完成端侧 MCP 的真实平台闭环，再补云端 MCP 接管形态；App 产品界面与配网完善随后推进

这份计划接替 [上一阶段计划](next-product-plan.md) 中的端侧语音模型开发顺序。群通话、房间名称、邀请码、静音保持和 NFC 组队行为继续沿用原产品定义

这项实测证明平台能够发现并调用同频工具。真实房间接入、固件双通道运行、云端 MCP 注册和真人语音仍由后续阶段验证；探测器仅记录调用，未建立对讲媒体

## 系统边界

| 组件 | 负责的事情 |
| --- | --- |
| 灵矽 App / App backend | 设备与用户关联、默认智能体、配网入口、智能体 MCP 配置；后续展示同频状态 |
| 灵矽平台 | OTA 配置与设备会话、ASR、LLM、TTS、设备工具发现与调用、云端 MCP 调用 |
| 同频固件 | 音频硬件、灵矽连接、同频控制连接、MCP 工具、NFC、对话与对讲的音频切换 |
| 同频控制服务 | 房间与邀请码、成员和恢复目标、设备操作投递及确认、云端 MCP 适配 |
| Janus | 群语音媒体、混音、房间隔离 |

固件保留灵矽 WebSocket 与同频控制 WebSocket 两条独立连接。群语音仍由现有 PeerConnection 承载。麦克风上行在灵矽与同频之间按模式选择，扬声器由同一个播放调度器管理

平台接入以公开协议为边界。旧小智仓库中的 OTA、WebSocket、MCP 和 BluFi 实现按模块参考移植；现有同频的板级音频、Opus、WebRTC 和房间逻辑继续使用。移植时记录来源提交与许可证

### 两类 MCP 的职责

**设备 MCP** 控制当前设备，固件直接接收平台 `tools/call`。工具发现随设备连接完成，适合“对这台设备说话，让它进入同频”的主路径

**云端 MCP** 是可配置给灵矽智能体、以后也可接入其他 MCP 客户端的同频服务。服务通过自己的设备连接表投递操作，适合 App 智能体或其他入口接管设备。当前阶段实现平台文档使用的 SSE 传输；后续其他客户端需要时增加 Streamable HTTP

平台注入的 `X-Linx-Device-Id` 表示发起对话的设备。App 虚拟设备与实体同频设备可能不同：云端工具使用明确的目标设备，或使用已配置的默认目标映射；目标归属由服务配置与设备关联关系解析

管理 API 的“设备工具描述”用于调整说明文字。真正执行来自固件工具注册，或云端 MCP 服务。房间业务保持在同频服务中，平台和 App 使用这些能力

## 设备行为与音频接管

| 当前状态 / 事件 | 选定行为 |
| --- | --- |
| 启动 | 建立灵矽连接和同频控制连接；默认灵矽待机，按现有规则恢复上次已确认且未主动退出的房间 |
| 灵矽对话 | 按键语音送平台，播放平台 TTS；平台通过工具决定房间操作 |
| NFC 触碰 | 本地解析事件，直接进入已有 NFC 入房流程；平台推理不参与触碰动作 |
| MCP 加入 / 切房 | 暂停原音频上行，执行统一房间操作；媒体确认成功后切换到目标房间并播报房间名和人数 |
| 对讲中普通讲话 | 音频发到同频房间；灵矽连接保留用于控制，群聊音频留在对讲链路 |
| 对讲中按住命令键 | 暂停房间上行，命令音频送灵矽，保持房间收听；操作结束按静音设置恢复 |
| 查询房间 | 返回名称、人数、邀请码；设备本地播报，邀请码逐位读出 |
| 主动退出 | 清除房间恢复目标，结束群媒体，回到灵矽待机 |
| 加入 / 切房失败 | 恢复操作前的模式和房间，保留用户静音设置 |
| 灵矽暂时断线 | 现有群通话持续；后台恢复平台连接，NFC 继续使用同频服务 |

音频模式管理是本轮主要固件工作：

- 一个模块决定麦克风去向、当前播放源、临时上行暂停和持久静音，避免两套连接各自改全局状态
- 接管时清理旧模式播放缓冲，过滤迟到 TTS；退出后恢复平台音频，避免旧回复重新播放
- 工具调用等待现有媒体确认后返回成功。长操作超时返回可查询的实际状态，区分“收到命令”和“已经入房”
- MCP 处理期间保持平台连接，先完成工具回包；当前轮次的 `abort` 会影响工具等待，接管阶段通过本地音频门控处理播放
- 房间名、人数和邀请码使用可组合的本地短音频反馈，使 NFC 直入和云端接管都能播报；常规智能体回答继续由平台 TTS 提供

## 最小工具与统一执行接口

| 设备工具 | 参数 | 执行结果 |
| --- | --- | --- |
| `self.intercom.join` | `invite_code`，六位数字字符串 | 当前模式、确认后的房间名与人数 |
| `self.intercom.switch` | `room_name`，已加入的编号房间名 | 切换后的房间、静音状态 |
| `self.intercom.status` | 无 | 模式、房间、人数、邀请码、静音状态 |
| `self.intercom.set_mute` | `muted` | 生效后的静音状态 |
| `self.intercom.leave` | 无 | 已退出、当前灵矽模式 |

上述设备工具使用普通 tool 类型供智能体发现。云端提供对应的 `intercom.*` 工具，增加目标设备选择，复用同一组操作语义。NFC 作为内部入口传入标签标识，沿用现有标签解析与组队规则

云端 MCP adapter 直接调用同频服务的操作投递接口；设备收到操作后走本地统一执行入口。操作携带唯一 ID，重复请求返回同一操作结果；响应与模式切换绑定当前操作，防止迟到结果覆盖新状态。离线设备返回离线状态，重新上线时依靠明确的恢复目标

历史平台还支持 `structuredContent.funcs` 调用设备 RPC。这条链路作为后续适配能力保留，本轮采用直接设备工具和云端控制投递两条清楚的入口

## 实施顺序与完成标准

任务按验收结果持续推进，不设时间、token 或费用预算，也不设置定时收尾。每阶段完成后直接继续下一阶段，直到本次设备与 MCP 转型完成。执行者从已合并基线建立新 worktree，模型与会话选项沿用用户当前选择

| 阶段 | 交付与验收 |
| --- | --- |
| 1. 平台工具接真实房间 | 复用现成测试智能体与软件设备，把工具探测器接到同频服务；真实平台调用触发测试端入房，并以房间确认和媒体证据验收 |
| 2. 固件默认接灵矽 | OTA / 设备 token、灵矽 WebSocket、设备 MCP、音频模式管理；构建 ESP32-S3 固件，用模拟平台和控制服务验证接管及返回 |
| 3. 云端 MCP 形态 | 同频 MCP adapter、设备投递与结果确认；本地客户端测试及灵矽平台接入测试，复用同一房间服务 |
| 4. 稳定性与交付 | 重复调用、平台断线、切房失败、静音保持、退出恢复、迟到 TTS；修复 review 问题，提交 PR 与运行交接 |

阶段 1 完成即可形成首个可评审提交；阶段 2 完成形成“灵矽设备接管同频”的阶段 PR，阶段 3 单独交付云端 MCP，控制每轮范围

阶段 PR 是进度节点，整体完成要求设备接入、真实平台工具调用、房间与媒体接管、退出恢复、云端 MCP 接入和相关回归均有证据。硬件或人工验收缺失时明确保留待验收状态，继续其余可执行工作；上下文压缩或会话恢复后从任务记录继续

## 后续产品化

1. **设备体验完整**：移植经过核实的 BluFi 修复，接入 NFC 读卡器、AEC、音量与房间反馈；完成两台嵌入式设备真实通话与连续运行验收
2. **App 设备能力**：沿用设备添加与默认智能体绑定，在设备页展示同频状态与邀请码；沿用智能体 MCP 配置入口选择同频服务
3. **可复用 MCP 产品**：完善默认目标选择、设备关联、服务认证与公网接入；支持其他 MCP 客户端，保留明确的工具结果和调用记录
4. **设备发布与多板型**：将已验证的协议、模式管理与板级配置分开；建立固件版本、OTA 发布和回滚流程，逐步接入其他灵矽设备

第一轮产品验收用一条流程：设备启动连接灵矽 → 智能体调用进入房间 → 群内通话 → 按键让智能体切房 → 退出回到灵矽对话。随后增加 NFC 直接入房和 App 智能体经云端 MCP 接管

## 验收与交接标准

每次交付列出源码和固件 SHA、实际平台会话、MCP 请求与返回、房间确认、媒体收发和模式变化。分别记录接口成功、模拟设备成功、固件构建通过、实体设备通过

测试覆盖一个完整成功流程，以及重复调用、设备离线、平台断线、无效邀请码、切房失败、静音切房、主动退出、迟到音频。沿用既有测试结果，新增验证集中在接管行为与双连接生命周期

本地交接记录实际仓库、worktree、分支、服务地址、job ID、运行模型、测试身份、凭据读取方式、未通过项和下一条命令。历史 App 与平台快照作为只读参考；实现改动集中在同频仓库
